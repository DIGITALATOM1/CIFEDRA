# CIFEDRA CONNECT: выбор платформ для решения

Дата: 2026-06-11  
Статус: рабочее решение v0.1

## Контекст

`CIFEDRA CONNECT` строится вокруг сценария `Need -> Match -> Prepare -> Connect -> Result`: пользователь формулирует задачу, получает релевантных людей, готовит разговор, выходит на контакт и фиксирует результат.

Из текущей продуктовой гипотезы следует, что мобильные приложения нужны точно. При выборе исполнителя, помощника, эксперта или наставника может потребоваться мобильная механика выбора: карточки, свайпы, быстрый shortlist, быстрый запрос контакта и коммуникация до результата.

Поэтому платформенное решение нужно разделять на три слоя:

1. Пользовательский продукт: мобильное приложение и ключевые пользовательские сценарии.
2. Операционный слой: базы, справочники, модерация, ручной матчинг, подготовка SRS и базы знаний.
3. Коммуникационный слой: поддержка, concierge-помощь, переписки, уведомления и эскалации.

## Решение

Целевую платформу нужно строить как гибрид:

| Слой | Рекомендация | Роль в продукте |
| --- | --- | --- |
| Mobile app | React Native + Expo | Основной пользовательский интерфейс iOS/Android: задача, карточки людей, свайпы, shortlist, подготовка контакта, статусы результата. |
| Core backend | Postgres-first backend, с API поверх бизнес-логики | Системный источник истины для пользователей, задач, профилей, матчей, свайпов, статусов, доверия, правил доступа и аналитических событий. |
| Baserow | Внутренняя операционная база и no-code backoffice | Справочники категорий `Life/Work/Skills`, профили кандидатов на раннем этапе, очереди модерации, ручной матчинг, реестр требований, SRS-база, knowledge base для отдела системного анализа. |
| Chatwoot | Коммуникационный слой support/concierge | Поддержка пользователей, управляемая коммуникация с оператором/агентом, эскалации, входящие обращения, первые concierge-сценарии выбора помощника. |
| Product chat | Отдельное решение после SRS | Если нужен прямой чат пользователь-исполнитель, его лучше проектировать как часть core продукта, а Chatwoot оставить для support/concierge. |

Ключевой принцип: Baserow и Chatwoot не должны становиться ядром конечного продукта. Они ускоряют операционную работу, аналитику, поддержку и ручные MVP-сценарии, но мобильная логика выбора исполнителя, свайпы, права доступа и результат контакта должны жить в собственном продукте.

## Сценарий выбора исполнителя

Минимальный пользовательский сценарий для MVP:

1. Пользователь выбирает направление: `Life`, `Work` или `Skills`.
2. Формулирует задачу и ожидаемый результат.
3. Приложение показывает карточки людей с кратким обоснованием релевантности.
4. Пользователь свайпает, добавляет в shortlist или запрашивает контакт.
5. Приложение готовит разговор: цель, контекст, вопросы, риски, следующий шаг.
6. Для первого MVP коммуникация может идти через Chatwoot как concierge-канал.
7. После контакта пользователь фиксирует результат: договорились, не подошел, нужен другой человек, нужен follow-up.

## Где использовать Baserow

Baserow имеет смысл использовать в следующих зонах:

| Зона | Пример данных |
| --- | --- |
| Категории продукта | `Life`, `Work`, `Skills`, подкатегории, словарь услуг, теги навыков. |
| Каталог людей для пилота | Роль, контекст, география, доступность, доверие, ограничения, источники проверки. |
| Ручной матчинг | Заявки пользователей, подборки кандидатов, комментарии аналитика/оператора. |
| Системный анализ | Реестр SRS, требования, статусы ревью, вопросы к бизнесу, traceability. |
| База знаний | Инструкции, RN, руководства, шаблоны постановок, реестр решений. |

Ограничение: не проектировать свайпы, чат, платежи, доверие, уведомления и мобильный UX как Baserow-only решение.

## Где использовать Chatwoot

Chatwoot имеет смысл использовать в следующих зонах:

| Зона | Пример сценария |
| --- | --- |
| Поддержка | Пользователь не понял, как выбрать помощника, и пишет в поддержку. |
| Concierge matching | Оператор помогает уточнить задачу и подобрать людей в раннем MVP. |
| Эскалация | Сложная задача уходит агенту/аналитику/оператору с историей переписки. |
| Операторские мобильные сценарии | Сотрудник отвечает пользователям с телефона через Chatwoot mobile app. |
| Help center | Публичные инструкции, FAQ, правила безопасного контакта. |

Ограничение: Chatwoot не стоит использовать как полноценный marketplace messenger, пока не определены роли сторон, модерация, приватность, вложения, блокировки, жалобы, хранение истории и юридическая модель.

## Варианты и оценка

| Вариант | Плюсы | Минусы | Решение |
| --- | --- | --- | --- |
| Baserow-only | Быстро, no-code, удобно для таблиц и внутренних баз. | Нет полноценного нативного мобильного приложения, слаб для свайпов, чата, прав доступа и сложной бизнес-логики. | Не использовать как core продукта. |
| Chatwoot-only | Быстрый старт коммуникаций, готовые операторы, mobile apps. | Это support desk, а не продуктовая платформа matching/swipe. | Использовать как support/concierge слой. |
| Custom mobile + Baserow + Chatwoot | Баланс скорости и контроля: мобильный UX свой, операционка быстрая, коммуникации готовы. | Нужна интеграционная архитектура и дисциплина по источникам истины. | Рекомендованный вариант для MVP. |
| Полностью custom | Максимальный контроль и масштабируемость. | Дольше старт, больше рисков на ранней проверке гипотез. | Вернуться после первых SRS и пилота. |

## Риски

| Риск | Как снизить |
| --- | --- |
| Baserow начнет использоваться как production core без контроля схемы. | Сразу определить, какие таблицы являются временными операционными витринами, а какие данные должны мигрировать в core backend. |
| Chatwoot смешает support и прямое общение пользователей с исполнителями. | Разделить `support/concierge` и `product chat` в требованиях. Для прямого чата подготовить отдельный SRS. |
| Свайп-механика станет поверхностной и ухудшит качество выбора. | В карточке кандидата показывать основание матча, доверие, ограничения, next best action, а не только фото/краткое описание. |
| Ранний MVP потеряет результаты контактов. | Сделать `Result` обязательным состоянием: итог, следующий шаг, оценка релевантности, причина отказа. |
| База знаний разрастется без структуры. | Вести решения по разделам `platforms`, `srs`, `product`, `business`, `support`, `agents` и фиксировать owner/status/date. |

## Следующие задачи для системного анализа

1. Подготовить SRS-блок `Platform Requirements`: мобильные приложения, backoffice, коммуникации, интеграции, данные, роли.
2. Описать роли: пользователь, исполнитель/помощник, эксперт, наставник, оператор, системный аналитик, администратор.
3. Развести два сценария коммуникации: `concierge via Chatwoot` и `direct product chat`.
4. Подготовить модель данных MVP: task, profile, candidate card, match, swipe, shortlist, conversation, result.
5. Сформировать реестр Baserow-таблиц для пилота и отметить, какие данные являются временными.
6. Подготовить mobile UX flow для выбора исполнителя: карточка, swipe, shortlist, запрос контакта, подготовка разговора.
